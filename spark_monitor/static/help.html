Coverage: девять проверок данных

  • Task metrics — есть executor run time.
  • Executor CPU time — есть CPU nanoseconds задач.
  • SQL events / plan / metrics — доступны события SQL, physical plan и accumulator metrics.
  • AQE events — есть adaptive plan updates.
  • Executor memory metrics — есть executor-level memory updates.
  • Application completed / log complete — зафиксирован конец приложения и лог не оборван.
03

Статусы и выбор итогового флага

Для каждой из семи областей парсер проверяет все правила. В строку приложения поднимается самый серьёзный найденный статус.

CRITЕсть критическое нарушение границы или высокий подтверждённый риск.
WARNЕсть отклонение или потенциальная оптимизация, требующая проверки.
OKДанных достаточно; ни одно правило области не сработало.
UNKNOWNПроверка применима, но в Event Log недостаточно прямых доказательств.
N/AПроверка неприменима: например, в physical plan нет join или scan.

Порядок серьёзности: CRITICAL → WARNING → OK. NOT_AVAILABLE и NOT_APPLICABLE не превращаются в проблему и не заменяются предположениями. Количество Critical / Warning в верхней панели — число приложений по их худшему статусу, а не число отдельных флагов.

1

Compute / resources

Отвечает на вопрос: эффективно ли приложение использовало выделенные CPU и достаточно ли в нём параллельной работы.

Активные границы CPU efficiency: WARN ≤ —, CRIT ≤ — Slot utilization: WARN ≤ —, CRIT ≤ — Peak slots ratio: WARN ≤ —, CRIT ≤ —

Метрики

Allocated CPU
CPU time задач / доступные executor core-ms. Показывает загрузку всей выделенной CPU-ёмкости.
Task-slot utilization
Executor run time задач / доступные task-slot-ms. Низкое значение означает, что slots часто простаивали.
Task CPU efficiency
Executor CPU time / executor run time. Отделяет вычисления на CPU от ожиданий, I/O и накладных расходов внутри task.
Running / available, avg
Среднее число одновременно работающих tasks / среднее число доступных slots.
Running / available, peak
Пиковые running tasks / пиковые slots; основа проверки недостаточного параллелизма.

Флаги

LOW_CPU_EFFICIENCY
Task CPU efficiency не выше границы.
RESOURCE_UNDERUTILIZATION
Task-slot utilization не выше границы. CRIT понижается до WARN, если приложение короче — и потеряно меньше —.
INSUFFICIENT_PARALLELISM
Peak running tasks / peak available slots не выше границы.
Формулы и источники Event Log

executor_cpu_time_ms берётся из Task Metrics Executor CPU Time; executor_run_time_ms — Executor Run Time. Доступная ёмкость интегрируется по executor timeline, поэтому учитывает появление и удаление executors во времени. Wasted core-seconds = max(0, core capacity − CPU time) / 1000.

2

Memory / GC / spill

Показывает давление на JVM и случаи, когда рабочие данные не поместились в execution memory.

Активные границы GC: WARN ≥ —, CRIT ≥ — Spill: WARN ≥ —, CRIT ≥ —

Метрики

GC time / ratio
Суммарное JVM GC Time и его доля от Executor Run Time.
Memory spill
Байты, временно вытесненные из execution memory.
Disk spill
Байты, фактически записанные на диск; обычно сильнее влияют на время.
Tasks with spill
Доля tasks, где memory или disk spill больше нуля.
Peak execution memory P95 / MAX
95-й перцентиль и максимум task-level Peak Execution Memory.

Флаги

HIGH_GC
GC ratio достиг warning или critical границы.
HEAVY_SPILL
Максимум из Memory Spill и Disk Spill достиг границы.
Формулы и источники Event Log

GC ratio = Σ JVM GC Time / Σ Executor Run Time × 100. Spill и peak execution memory суммируются или распределяются по успешным task attempts; повторные failed attempts не смешиваются с фактическим результатом stage.

3

Data skew / stragglers

Ищет stage, где небольшая часть задач заметно дольше или обрабатывает больше данных, чем медианная задача.

Активные границы Анализируется stage с ≥ — tasks P95 / median: WARN ≥ —, CRIT ≥ — MAX / median: CRIT ≥ —

Метрики

Duration P95 / median
Насколько медленные 5% tasks отличаются от типичной task.
Input P95 / median
Неравномерность входных байтов между tasks.
Shuffle P95 / median
Худший из факторов shuffle read и shuffle write.
Duration MAX / median
Отношение самой долгой task к медиане.
Skewed tasks
Доля tasks дольше median × —.
Worst stage
Stage с максимальным duration P95 / median среди пригодных для анализа.

Флаги

DATA_SKEW
Duration нарушает границу и хотя бы один data-volume factor также достигает warning.
TASK_STRAGGLERS
Duration нарушает границу, но доступные распределения объёма данных её не подтверждают.
Формулы и ограничения

Все отношения считаются внутри одного stage attempt по successful tasks. Stage с меньшим числом tasks не получает оценку: на малой выборке P95 нестабилен. Если median равна нулю или распределение отсутствует, соответствующий factor не выдумывается и остаётся недоступным.

4

Shuffle pressure

Показывает цену перераспределения данных между executors и долю времени, потраченную на ожидание remote blocks.

Активные границы Fetch wait: WARN ≥ —, CRIT ≥ — Shuffle / input: WARN ≥ —, CRIT ≥ —

Метрики

Shuffle read / write
Физически прочитанные и записанные байты shuffle.
Total shuffle
Shuffle read + shuffle write.
Fetch wait
Время fetch wait и его доля от Executor Run Time.
Shuffle / source input
Total shuffle / bytes, прочитанные из исходных источников.
Remote read
Remote shuffle bytes / (remote + local shuffle bytes).

Флаги

SHUFFLE_FETCH_WAIT
Доля fetch wait достигла warning или critical границы.
HEAVY_SHUFFLE
Отношение total shuffle к source input достигло границы.
Как интерпретировать

Большой объём shuffle сам по себе не всегда проблема: для крупного входа он может быть естественным. Поэтому флаг использует отношение к source input. Fetch wait отдельно показывает сетевое/дисковое ожидание, которое может быть высоким даже при умеренном объёме.

5

Scan / partition pruning

Проверяет pruning по прямым evidence physical plan и файловым счётчикам, а не по наличию фильтра в SQL-тексте.

Активная граница Большой scan без pruning: read ≥ — File pruning % = skipped / (skipped + selected) × 100

Метрики

Read / Rows
Байты и строки, реально прочитанные scan-оператором.
Selected files
Файлы, оставшиеся после выбора source scan.
Skipped files
Кандидатные файлы, исключённые source-level pruning.
File pruning %
Доля исключённых файлов среди selected + skipped.
Filters captured
В physical plan присутствуют partition, pushed или data filters; это evidence, но не самостоятельное доказательство фактического pruning.

Флаги и состояния

NO_PARTITION_PRUNING
Есть partitioned source, но scan выбрал все кандидатные файлы. Статус WARN.
LARGE_SCAN_WITHOUT_PARTITION_PRUNING
То же самое, а read достиг активной границы. Статус CRIT.
PRUNING_DETECTED
Есть ненулевой счётчик skipped files; карточка может быть OK.
UNKNOWN
Не хватает файловых счётчиков для доказательства; итог UNKNOWN, а не WARN.
SOURCE_NOT_PARTITIONED
Источник не partitioned; проверка получает N/A.
Почему фильтр в запросе ещё не означает pruning

PartitionFilters показывает, что условие дошло до physical plan. Фактический результат подтверждают source file counters: сколько файлов было рассмотрено, выбрано и пропущено. Поэтому карточка различает «фильтр найден», «pruning подтверждён» и «проверить невозможно».

6

Join pathologies

Проверяет раздувание строк после join и показывает случаи, где небольшую сторону, возможно, стоило broadcast-ить.

Активные границы Row amplification: WARN ≥ —, CRIT ≥ — Broadcast threshold берётся из effective Spark configuration конкретного приложения

Метрики

Join strategy / type
Например, SortMergeJoin, BroadcastHashJoin и тип inner/left/right.
Left / right rows
Выходные строки дочерних операторов, когда SQL metrics позволяют их связать.
Output rows
Количество строк после join.
Row amplification
Output rows / max(left rows, right rows).
Broadcast candidate
Известная сторона меньше effective auto broadcast threshold, но стратегия не broadcast.

Флаги

JOIN_ROW_EXPLOSION
Row amplification достиг warning или critical границы.
POTENTIAL_BROADCAST_CANDIDATE
Потенциальная оптимизация со статусом WARN. Это подсказка, а не гарантия, что broadcast безопасен.
No joins
Physical plan проверен, join нет — область получает N/A.
Что показывает Show all joins

Каждая строка соответствует join node физического плана и содержит только реально доступные метрики. Пустое значение не заменяется нулём. Stage IDs и SQL execution ID используются для связи с исходными событиями.

7

Expensive SQL operators

Собирает тяжёлые Window, Sort, Exchange и операторы, резко увеличивающие число строк.

Активные границы Window input ≥ — Sort input ≥ — SinglePartition shuffle ≥ — Row expansion: WARN ≥ —, CRIT ≥ —

Метрики

Window / Sort / Exchange
Количество соответствующих nodes в physical plan.
Largest Window input
Максимальное число строк на входе Window.
Window upstream shuffle
Объём ближайшего upstream shuffle перед Window.
Largest Sort input
Максимальное число строк, обработанных Sort.
Largest Exchange output
Максимальный shuffle output среди Exchange.
Max Generate / Expand amplification
Output rows / child output rows для операторов развертывания.

Флаги

HEAVY_WINDOW
Window input достиг границы.
HEAVY_WINDOW_AFTER_SHUFFLE
Тяжёлый Window следует за shuffle/sort.
HEAVY_SORT
Sort input достиг границы.
SINGLE_PARTITION_BOTTLENECK
SinglePartition Exchange записал не меньше заданной границы; статус CRIT.
ROW_EXPANSION_OPERATOR
Generate/Expand увеличил поток строк до warning или critical уровня.
Источники и область применимости

Операторы извлекаются из Spark SQL physical plan, значения — из SQL accumulator metrics. Если plan отсутствует, область получает N/A. Счётчик операторов без row/byte metrics остаётся полезным, но не используется для порогового флага.
